# day06 · 结构化输出与校验重试

日期：2026-11-28 ｜ 阶段：W1 D6

## 做了什么

`extractor/`：Pydantic 定义 schema（todo/owner/due/evidence）→ 调 API 拿 JSON →
`model_validate` 校验 → 失败把错误回灌给模型重试（最多 3 次）。

## 第一轮：10 条样本，全部一次通过

| 指标 | 结果 |
|---|---|
| JSON 合法率 | 10/10 |
| schema 通过率 | 10/10 |
| 平均尝试次数 | 1.00 |

**这组数据说明实验不算数**：重试分支一次都没走到。
内容质量抽查还行（闲聊、通知类输入正确输出 0 条），但"重试"这个核心机制没被验证。

## 第二轮：故意让 schema 比 prompt 更严

schema 要求 `priority ∈ {高,中,低}`，但 system prompt 里完全不提这个字段。

| 尝试 | 结果 | 错误 |
|---|---|---|
| 1 | ✗ | `priority` 缺字段（Field required）|
| 2 | ✗ | 填了"未提及"，不匹配 `^(高|中|低)$` |
| 3 | ✓ | 填"中" |

## 四条结论

1. **重试不是"重跑"，是"带着错误信息重跑"。**
   第一次报错只说 `Field required`，模型不知道取值范围；第二次报错带了 pattern，
   它才收敛。**Pydantic 的报错文本天生适合回灌**——里面写着约束本身。
   这就是用 schema 库而不是手写 if 判断的真正理由。
2. **合法 ≠ 正确。** 第三次通过了，但三条待办的 priority 全是"中"——原文根本没提优先级，
   模型编了一个"看起来合理"的值。**schema 保证形状，重试保证能过，都不保证内容对。**
3. **过度抽取仍然存在。** "登录改版灰度 10%，没有异常"是进展汇报，没有可执行动作，
   却被抽成了一条待办。JSON 合法、字段齐全、内容错——这类错误只能靠评测集发现（W8）。
4. **重试有成本。** 3 次调用 = 3 倍 token、3 倍延迟。正确顺序是：
   先把 prompt 写清（降低失败率），再用重试兜底（保险，非常态）。

## 工程模板（以后所有项目都这么写）

```
schema 定义数据结构
  ↓
prompt 说清规则 + json_object
  ↓
json.loads → pydantic 校验
  ↓ 失败
把 errors() 原样回灌 → 重试（上限 2–3 次）
  ↓ 仍失败
返回明确的失败信号，不要返回半成品
```

最后一条最容易被忽略：**重试耗尽后必须"大声失败"**，不能把残缺结果当成成功往下传。
